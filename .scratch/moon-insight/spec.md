# MoonInsight 需求记录

> 定位：这不是一次定稿的完美需求文档，而是**当前想法的记录**。需求会随盘问与实现进展持续变动，本文件随时更新。技术选型调研见 `framework-selection.md`。

## 项目定义

金融助手 Agent：以 AI Agent 形态提供金融助手能力的项目。（术语与领域定义见 `CONTEXT.md`）

## 项目定位与工程原则

- **项目形态**：可公开展示的参考级实现——仓库整体（代码、文档、选型记录、过程决策）是交付物，须经得起外部评审
- **交付形态**：web 聊天界面为主（`web/` 已激活，见盘问第一轮 Q3 与第二轮决策）；FastAPI + SSE 条件锁随流式场景激活；部署方式届时再定
- **决策原则**：一切选型与工程决策兼顾「成品可展示」与「方法论可沉淀」；过程记录（盘问、选型、ADR）与代码同等重要，不做一次性的隐性决策

## 选型原则

不在一开始锁死所有步骤的所有技术栈。区分两类：

- **架构性必选**：贯穿全程、换不掉的——现在锁定；
- **步骤性选型**：向量库、任务调度、前端、数据库、部署等——保持端口化，到步骤再定。

## 已锁定决策

1. **LLM 接入层：OpenAI SDK 兼容格式** + LLMProvider 端口——国内主流 API 几乎全兼容，一个 SDK 通吃；自带重试、流式、usage 返回。
2. **结构化输出（JSON Schema 约束）+ 确定性代码校验**——LLM 出 schema 约束的提案，代码校验后执行；合规红线只能用确定性代码保证，不靠 LLM 自觉。
3. **评估闭环（EDD：golden set + LLM-judge）+ 可观测**——Langfuse（OSS 自托管）为默认工具；「无评估不 Agent」。
4. **编排最终形态：LangGraph**——先手写循环，复杂度起来再上框架。
5. **工具协议：MCP**——框架基础能力（见盘问第二轮）；把端口包装为 MCP server，与内部端口并存。
6. **交付形态（条件锁）：FastAPI + SSE 流式**——web 聊天界面为主（见盘问第一轮 Q3）；具体流式方式（SSE 等）待定。

## 明确不锁（端口化，到步骤再定）

向量库（Chroma → pgvector/Qdrant，按规模换）、任务调度（APScheduler → Celery，按量递进）、前端（Next.js 体系）、数据库（SQLite → PostgreSQL）、部署（Docker Compose → K8s）。

## 盘问确认的决策

### 第一轮

**Q1 · 任务范围**：金融助手 Agent 具体做什么？任务范围决定 domain/ 与 pipeline/ 的内容。
**A**：大致是交互问答助手；当前业务不是重点，先定义好基本框架。
**决策**：业务定位 = 交互问答助手；业务细节后置，优先定义基本框架。

**Q2 · 首个验证对象**：hello world 已通、骨架已建，接下来该验证什么？
**A**：质疑我推荐中「评估等属后续阶段」这一时序说法的出处——经查证，该说法来自未确认的提案，作废。
**决策**：framework-selection.md 的阶段性划分是未确认提案，随框架定义重定。

**Q3 · 交互形态与网站**：条件锁与 `web/` 槽位何时激活？
**A**：web 不是已经启用了吗？
**决策**：`web/` 已激活（hello world 阶段即定）；交付形态以 web 聊天界面为主。

**Q4 · 多用户与鉴权**：何时引入？
**A**：鉴权能否后期注入？是否仍在构想中？
**决策**：鉴权后期注入——交付层中间件预留注入点即可；当前不设计、不锁。

**Q5 · 模型与预算**：DeepSeek 起步是否延续？
**A**：起步用什么模型不重要——重要的是接口结构；DeepSeek 与其他模型接口结构一致（OpenAI 兼容）。
**决策**：起步模型是配置项而非选型；锁定的是 OpenAI 兼容接口结构（已锁决策 ①）；DeepSeek 仅为配置首例。

**Q6 · 合规红线**：不预测涨跌、无事实错误、不输出确定性投资建议，是否延续为硬约束？
**A**：免责声明是需要的。
**决策**：免责声明保留——研究用途，不构成投资建议。

### 第二轮（方向调整——用户直接给出框架方向）

**Q**：第二轮前沿（分层线、循环形态、首个验证对象、端口清单、SSE 时机、CLI 地位）如何收敛？
**A（用户方向）**：先完成大致的问答框架——不限制于当前的具体金融业务场景，与场景无关；模型要有 Function Calling、Tool、MCP 等基础能力；页面流式输出（或其他输出方式）。
**决策**：
1. 构建顺序：先完成通用问答框架——与金融业务场景解耦，场景无关
2. 框架基础能力：Function Calling、Tool 机制、MCP 接入、页面流式输出
3. 业务后置：金融场景作为「工具集 + prompt」在框架完成后填入，不改变框架
4. 交付形态：web 聊天界面为主（流式）

## 用户拍板决策（盘问暂停后）

1. **前端布局**：`web/` 采用 src/ 布局——`src/app/` 路由壳；`src/main/` 下按 domain（类型）/ page（界面）/ 跨域通信层分区（已迁移完成）
2. **前端结构约定**（具体规则，随框架实现落地）：
   - 路由壳与业务组件分离：`src/app/` 只放路由入口，业务界面放 `src/main/page/`
   - 类型独立于 UI：领域类型（消息、会话、工具调用事件等）放 `src/main/domain/`
   - 页面按业务域组织：界面组件按域分组，而非按技术类型（components/hooks 式）分组
   - 跨域通信设施独立一层：请求封装、流式客户端、认证注入等被多个域共用的技术设施放共享位置（命名待定），不塞进任何业务域
   - 单域业务服务 colocate 域旁：只服务一个域的服务逻辑与它的类型放同一目录
3. **流式体验**：问答场景采用流式输出——适合长文本与工具调用进度展示；具体流式方式（SSE 等）待定
4. **演进策略**：采用五阶段演进路径——① 先跑通一次工具调用 → ② 包成带步数上限的 Agent 循环 → ③ 加真实工具 → ④ 加记忆与状态 → ⑤ 再上编排框架（来源：[Scrimba: How to Build AI Agents](https://scrimba.com/articles/how-to-build-ai-agents/)）。架构阵营按三分法定位：当前走「供应商 API 之上的自研薄封装 + MCP」阵营，复杂度起来后迁 LangGraph（与已锁决策 ④ 一致；来源：[O'Reilly: The AI Agents Stack](https://www.oreilly.com/radar/the-ai-agents-stack-2026-edition/)）。行业缺口「89% 有可观测 vs 仅 52% 有评估」是本项目差异化空间——评估先行
5. **阶段 ① 验证物的定性**：四则运算（calculator）属**测试验证内容**——它是验证「工具调用链路」的脚手架，不属于框架业务；业务工具由业务阶段提供，届时该示例移入测试或移除
6. **走通的定义（前后端联动）**：后续阶段的「走通」= **前端参与的完整链路**——用户在前端页面发起对话，后端 Agent 处理，结果（含流式）回到前端渲染；仅后端测试通过不算走通。阶段 ① 已完成：后端集成测试与前端联动（经 dev 代理的真实问答闭环）均已验证
7. **后端分层对齐四层架构**：`domain/`（纯逻辑 + 端口抽象，含 `domain/ports/` 与 `domain/shared/`）/ `application/`（用例编排）/ `infrastructure/`（端口实现）/ `interfaces/`（FastAPI 交付与组装）——与既有惯例统一，替代原 ports/adapters/pipeline/api 命名切法
8. **仓库形态对齐平级项目**：前后端各为完整项目平级存放——后端 `app/`（Python 项目：pyproject + `src/moon_insight/` 四层 + `_tests_/`，src 布局）、前端 `web/`；根目录只放 harness 与跨项目资产
9. **前端样式方案定稿**：Tailwind CSS v4 + shadcn/ui + OKLCH 设计令牌（shadcn 官方注册表不可达时手工落地源码，components.json 保留别名指向 `@/main/page/shared/ui`）；基础组件进 `src/main/page/shared/ui/`；以通用 Agent 视角选型，不绑定任何业务主题
10. **阶段 ② 循环参数**：Agent 循环步数上限 4 轮（MAX_STEPS）；触达上限后再请求一次最终回答并标记 hit_limit；响应携带 steps/hit_limit 供运行记录与前端展示
11. **E2E 沉淀方案与 fake 定位**：浏览器流程固化为仓库内 Playwright E2E（`web/e2e/` + `@playwright/test`），webServer 自动拉起前端（5174）+ fake 后端（8001），端口刻意避开开发环境（5173/8000）；测试策略 fake 为主（`MOON_INSIGHT_LLM=fake` 注入 DemoLLM）+ 真实 LLM 可选（有 key 时跑，pytest 已有 skipif 模式）；Fake LLM 定位于 infrastructure（端口实现，长期回归线组成部分，区别于 demo_tools 脚手架）——ScriptedLLM 纯回放器（脚本显式注入、零理解逻辑、脚本耗尽抛错）+ DemoLLM E2E 演示回放器（两条封顶路径，路径穷举归 pytest 层）；前端 dev 代理目标 env 化（`MOON_INSIGHT_BACKEND_URL`，默认 8000）
