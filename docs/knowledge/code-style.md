# 代码规范

> 适用范围：所有 AI 工具产出的代码。审查时逐条对照本文件。

## 代码设计三大硬约束

1. **关注点分离**：每个函数/类只做一件事——能用「and」描述两个职责就该拆分。业务逻辑与基础设施分离：使用端只组装、编排层不含 HTTP 细节、纯逻辑不碰 IO。UI 展示与状态分离：展示组件只渲染，数据获取走通信层
2. **消除代码重复**：相同逻辑出现两次 → 提取共用函数；相似结构出现三次 → 抽象通用模式；跨模块的相同校验/转换 → 抽到共享模块。**但**业务语义不同的相似代码允许保留差异——不为消除重复而过早抽象
3. **抽象层次统一**：一个函数内的操作保持同一抽象层次——不能一行调用高层 API、下一行操作底层细节。跨层调用必须走明确接口。命名反映抽象层次：低层实现用具体名词，高层接口用业务动词

## 执行四准则

1. **先想后写**：动手前声明假设；需求存在多种解释时列出所有选项，而非悄悄选一个；遇到不明确的地方，停下来、说出来、问清楚。不假设——去验证
2. **简单至上**：只写解决问题所需的最少代码。不加需求之外的功能；不为单次使用的代码创建抽象；不添加未被请求的「灵活性」；不写推测性代码。自问：「一个高级工程师会觉得这过度设计了吗？」
3. **外科手术式修改**：只触碰必须改的代码；匹配现有风格，即使你觉得有更好的写法；删除自己的修改导致不再使用的 imports/变量/函数。不顺路优化相邻代码、不重构没坏的东西、不清理改动范围之外的内容。自我检查：改动的每一行都应能追溯到需求
4. **目标驱动执行**：把任务转化为可验证的目标（「修复这个 bug」→「写一个能复现的测试，然后让它通过」）；多步骤任务先给简要计划，每步有验证检查点；循环直到验证通过。不依赖「能跑就行」式的模糊标准

## 审查对照（不合格信号）

| 准则 | 不合格信号 |
|---|---|
| 先想后写 | 缺需求分析，直接跳到实现 |
| 简单至上 | 过度设计、单次使用的不必要抽象、死代码 |
| 外科手术 | diff 含无关文件的变更、顺手重构 |
| 目标驱动 | 无测试，或测试只覆盖 happy path |

## 栈内落点

- Python：关注点分离即依赖方向——`api/` 组装、`pipeline/` 编排、`domain/` 纯逻辑（见 `architecture.md`）
- 前端：`src/app/` 路由壳、`src/main/page/` 展示组件、通信层独立——UI 与数据获取分离
